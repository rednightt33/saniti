Every new refusal follows AGENTS.md "Gates and evidence":

## 0. Switch and invariants

- `EDGE_MULTIUSER` (edge-bff variable, default `false`).
  - **Off:** sign-in uses `EDGE_LOGIN`/`EDGE_PASSWORD_VERIFIER` exactly as today. The resulting principal is user #1
    (`owner_key = EDGE_OWNER`, role `admin`, every capability). Registration, code and reset routes answer 404.
  - **On:** sign-in reads `edge_bff.users`/`identities`.
- **Behaviour with the switch off is identical to today for the current user.** Test: the whole existing suite passes
  unchanged with the switch off (only the tests named in this contract may change).
- **The owner of a request comes only from the principal.**
  - No route, store call, worker call or Orc call reads `settings.owner` after Phase 1.
  - A test greps `apps/edge-bff/app` for `settings.owner`: the only allowed uses are the seed and the switch-off mapping in
    `app/principal.py`.
- **No plan or role name appears in code outside the catalog seed migration.** A test greps for the plan keys.
- Indicators keep being computed in the browser (user 2026-11-16). The server decides only which definitions, code
  chunks and data files a principal receives, and refuses ids outside the principal's capabilities.

## 2. Principal

```
Principal(user_id, owner_key, username, role, plan_key, status, expires_at, mfa_ok, capabilities: frozenset[str],
          limits: dict[str, value], version: str, token)
```

- **Resolution.** One query joins `sessions`, `users`, the active subscription, `plan_capabilities` and the overrides.
  - Switch off: `version` = `"env"`; capabilities = `{"*"}` (every capability).
  - A `disabled` user, a revoked or expired session, or an idle session beyond `EDGE_SESSION_IDLE_SECONDS` (default
    28800) answers 401.
  - An expired subscription resolves to the default plan (`free`).
- **`last_seen_at`** is updated at most once per 60 s per session.
- **Dependencies** (in a new `app/principal.py`, used by every router):
  - `principal` replaces `session`;
  - `writer` replaces `write` (CSRF as today);
  - `need("<capability>", write=False)` refuses with `CAPABILITY_REQUIRED`;
  - `admin(write=…)` = `need("admin.access")` plus `mfa_ok`.
- **Router signature.** Routers move from `routes(app, session, write)` to `routes(app, auth)`. `auth` exposes
  `principal`, `writer`, `need` and `admin`. Inside a handler use `p.owner_key`, `p.can(cap)` and `p.limit(cap)`.
- **`request.state.owner`** (EXEC-BACKTEST-REVAMP P5) stays, set from the principal.
- **`rights.py`** (P5): `rights_of(settings, owner)` becomes `rights_of(principal)`, which reads capabilities. The right
  `flow_point_in_time` becomes the capability `backtest.flow_point_in_time`, granted to plan `admin` in the seed.
  `EDGE_ADMIN_OWNERS` stays as the switch-off source until the switch is on, then it is retired.

## 3. Error contract (every edge-bff refusal, including FastAPI's own)

- **Shape:** `{"error": {"code": "...", "message": "...", "details": {...}}}`. FastAPI's `HTTPException` and validation
  errors are mapped to this shape (M471).
- **Codes and how the front-end reacts:**

| Status | Code | Front-end reaction |
|---|---|---|
| 401 | `UNAUTHENTICATED` | go to sign-in |
| 403 | `CSRF_INVALID` | re-read the session once, retry once |
| 403 | `CAPABILITY_REQUIRED` (`details.capability`, `details.display_name`) | show the upgrade prompt; keep the session |
| 403 | `PLAN_EXPIRED` | show the upgrade prompt; keep the session |
| 403 | `MFA_REQUIRED` | ask for the code |
| 403 | `ORIGIN_REJECTED` | unchanged |
| 404 | `NOT_FOUND` | another user's item, so nothing reveals that it exists |
| 429 | `LIMIT_REACHED` (`details.limit`, `retry_after_s`) | show the limit message |
| 429 | `SIGN_IN_RATE_LIMIT` | show the wait message |

- `Retry-After` is set on every 429.
- Messages are plain English, like every EDGE interface label (EXEC-UI-1019B, user: "Ok 1 aja"), in
  `static/edge-labels.js` (front-end) and `app/errors.py` (back-end); no internal names. Corrected 2026-11-16: the first
  draft said Indonesian.

## 4. Authentication flows (switch on; OWASP Authentication and Forgot Password cheat sheets, NIST 800-63B-4)

**Routes** (POST, Origin + body limits as today; every refusal per section 3):

| Route | Body | Answer |
|---|---|---|
| `POST /api/v1/auth/register` | `username`, `first_name`, `last_name`, `email`, `phone`, `password`, `password_repeat` | **always 202** `{"status":"CODE_SENT"}` for valid input (see below); 400 only for malformed input |
| `POST /api/v1/auth/register/verify` | `email`, `code` | 200 plus session cookie (user signed in directly, user decision); wrong, expired or used code → 400 `CODE_INVALID_OR_EXPIRED`, the same for every reason |
| `POST /api/v1/auth/code/resend` | `email`, `purpose` | always 202 |
| `POST /api/v1/auth/sign-in` | `login` (username or email), `password` | 200, or `MFA_REQUIRED` with a pending session for admins, or 401 `INVALID_CREDENTIALS`. Unverified account: the same 401 unless the password is right, then 403 `EMAIL_NOT_VERIFIED` (only after a correct password, so no enumeration) |
| `POST /api/v1/auth/password/forgot` | `email` | always 202 |
| `POST /api/v1/auth/password/reset` | `email`, `code`, `password`, `password_repeat` | 200 `{"next":"sign_in"}`, with every session revoked and a notification email; no automatic sign-in (OWASP) |
| `POST /api/v1/auth/password/change` | `current_password`, `password`, `password_repeat` | writer; other sessions revoked; notification email |
| `POST /api/v1/auth/sign-out` | — | as today |
| `POST /api/v1/auth/sign-out-all` | — | every session of the user |
| `POST /api/v1/auth/mfa/enroll` | — | `otpauth://` URI plus 10 recovery codes, shown once; admin only |
| `POST /api/v1/auth/mfa/verify` | `code` or `recovery_code` | sets `mfa_passed_at` |
| `GET /api/v1/auth/config` | — | public, no session: `{"multiuser": bool}`. The sign-in page shows "Create account" and "Forgot password?" only when true (added 2026-11-16 for the page builder) |
| `GET /api/v1/auth/session` | — | today's keys unchanged (`authenticated`, `login`, `csrf_token`, `capabilities` = configuration flags) plus `username` and `access: {plan, role, status, expires_at, mfa_ok, capabilities:[…], limits:{…}, version, owner_key, mfa_enrolled, seed, next: null/"verify"/"mfa"/"pay"}`; `seed` is true only for user #1 (the switch-off principal or the seed row): a browser with no last-login mark keeps its state only for it (section 12) |

**Registration rules:**
- Enumeration: an existing email or username gets the same 202. An existing email receives "akun sudah ada, gunakan
  Lupa Password".
- Username taken: the conflict is decided at verify time. The pending registration with a taken username gets
  `USERNAME_TAKEN` only after the email code is proved (the code owner may choose another).
- Password:
  - 8 to 256 characters (user decision; NIST/OWASP ask 15 without MFA, which is recorded);
  - every character allowed, no composition rule;
  - refused when found in Pwned Passwords (k-anonymity range API `api.pwnedpasswords.com`, 2 s timeout). If the API
    fails, accept and log `PWNED_CHECK_UNAVAILABLE` (fail-open; recorded decision);
  - stored with scrypt as today.
- Phone: E.164, normalised; Indonesian `08…` becomes `+628…`; not verified.
- A `pending` user is deleted 24 h after creation if never verified.

**Codes:**
- 6 decimal digits from `secrets`, 300 s validity, at most 5 tries per code.
- A new code does **not** reset the failed count of the day (NIST): at most 20 failed tries per user per day, then codes
  are refused for 24 h (`LIMIT_REACHED`).
- Resend at most once per 60 s and 10 per day per email.
- Codes are compared in constant time.

**Throttle** (Postgres, works with several replicas):
- Sign-in: 10 failures per email or username per 15 min, and 30 per IP hash per 15 min.
- Email sending: 10 per IP hash per hour.
- A dummy scrypt verify runs for unknown logins, so timing matches.
- **Client IP:** from `X-Forwarded-For` as set by Railway's edge (right-most untrusted hop). Until a probe proves what
  Railway sends (Phase 0 task, M470 notes), the per-IP limits are recorded in the table but not enforced; the per-account
  limits are enforced. The probe result is recorded in `ERRORS_AND_SOLUTIONS.md`.

**Sessions:**
- Absolute lifetime 24 h (today); idle timeout 8 h; at most 5 sessions per user (the oldest is revoked).
- Revoke all on password change or reset, disable, or role change.
- The SSE stream re-checks the principal on each loop (it already re-reads the session, `main.py`).

**Admin MFA:**
- TOTP (RFC 6238, SHA-1, 30 s, 6 digits, ±1 step, `last_step` replay guard).
- Required for role `admin` before any admin route. The current user (#1) enrols on first sign-in with the switch on.
  Switch off: no MFA, as today.

## 4b. Account preferences on the server (Phase 1; user decision 2026-11-16)

- **Table** `edge_bff.user_preferences`: (`owner_key`, `pref_key`) PK, `value jsonb` (size cap per key, e.g. 64 KB),
  `updated_at`, `version`.
  - Keys are the storage-registry entries of class `user` that are preferences or saved items, not caches. Examples:
    `ml.my`, `ml.ind.favs`, `ml.assets.v1`, `edge-model-choice`, `scr.extraCols`, `scr.last`, the Terminal chart
    settings.
  - The registry gains a `sync: true` flag. A test fails when a `user` key with no server copy is neither `sync` nor
    marked `cache`.
- **Routes:**
  - `GET /api/v1/preferences` returns this user's keys.
  - `PUT /api/v1/preferences/{key}` (writer) uses optimistic versioning: on a stale version it answers 409 with the
    current value.
  - Limits per user: key count and bytes.
- **Client** (`shared/edge-session.ts`):
  - after the session read, it loads the server copy into memory and storage;
  - writes go to both, the server debounced;
  - on the first sign-in after this ships, a local value with no server copy is uploaded once, only when the page
    identity equals the login that wrote it.
- **Sign-out** keeps clearing the browser (Phase 0), so nothing remains on a shared computer and nothing is lost.

## 5. Email

- **Switches:**
  - `EDGE_EMAIL_MODE` = `log` (default; writes the rendered email into the outbox row and the log with the code masked
    except in `EDGE_ENVIRONMENT=local`) or `resend`;
  - `RESEND_API_KEY`;
  - `EDGE_EMAIL_FROM` (for example `EDGE <no-reply@mail.<domain>>`);
  - `RESEND_WEBHOOK_SECRET`.
- **Sender loop:**
  - It runs beside the backtest loop, under its own switch `EDGE_EMAIL_ENABLED` (default `true` with the worker), and
    never waits behind an AI run.
  - It claims with `FOR UPDATE SKIP LOCKED` and a lease, and POSTs `https://api.resend.com/emails` with
    `Idempotency-Key: <idempotency_key>`.
  - Backoff 5 s, 30 s, 2 min, then `failed`.
  - A code email past `expires_at` becomes `expired`, never sent.
  - The payload is nulled once sent.
  - Registration inserts the code row and the outbox row in one transaction and wakes the loop.
- **Inbound webhook** `POST /api/v1/hooks/email/resend`:
  - Svix signature over the raw body, timestamp tolerance 5 min.
  - UNIQUE `svix-id`.
  - Bounce or complaint → `email_suppression`.
- **Templates:** plain English text plus simple HTML (the EDGE interface language, EXEC-UI-1019B), one file per purpose,
  in `app/email_texts.py`. Subject for codes: "Your EDGE code: 123456".

## 6. Hooks route exemption (payments and email)

- The Origin check (`main.py` `protections`) skips exactly the prefix `/api/v1/hooks/`.
- The body size cap and the security headers stay.
- A hook route has no session or CSRF; it must verify a signature over `request._body`.
- A route-table test refuses any other route under that prefix without a signature check.

- `list`: an array of strings.

## 15. New tabs and changes on `main` since the audit (delta inspection 2026-11-16, spot-checked)

- **Per-request owner is half done.**
  - `main.py` `session` sets `request.state.owner`.
  - Backtest uses it (`backtest.py` `identity`/`writer`).
  - The Screener still sends `owner=self.settings.owner` to the worker (`screener.py:676`) and binds it for lanes, items
    and preview slots (`:953`, `:969`).
  - The Watchlist binds `owner = self.settings.owner` (`watchlist.py:287`).
  - Phase 1 moves all of them to the principal.
- **Overview, Radar, Watchlist page files** (`app/pages.py` `PageFiles`):
  - `GET /api/v1/<family>/index` and `/file/<name>?sha=` use the session only.
  - They are served from process caches shared by every user (index 30 s; bytes by sha, 32 MB).
  - Every grant goes to the one gateway account under `quota.REF`.
  - Phase 3: a capability check (`<family>.view`, and per file kind such as `overview.day`, `radar.board`) runs **before**
    the shared cache.
- **Page files are cached by the browser for a year** (`app/pages.py:173`, `private, max-age=31536000, immutable`).
  - The browser would hand admin Radar files to the next user of that browser without asking the server.
  - Phase 3: `no-cache` (revalidated against the server's capability check) or one URL per capability.
- **Orc history mode CLIENT trusts a body `conversation_id`** (C2, `apps/market-ai-orc/app/main.py` ~773-784). Kept
  tables, run memory, exports and evidence are keyed by conversation only. Fixed in the Phase 0 fix round: a CLIENT run
  never opens a conversation its owner does not hold.
- **Radar data inside the Watchlist file** (new defect M476). `watchlist-stocks` carries the Radar screens of the newest
  date and flow values (`apps/terminal-publisher/watchlist.py:11, 33-35`). The Radar is an admin page. Phase 3 splits
  the file (base vs Radar badges) or publishes one per capability.
- **Watchlist limits** `LISTS=20`, `PER_LIST=50`, `INDICATORS=8` (`watchlist.py:29-31`) become plan limits. Its indicator
  keys are checked against the release and plan catalog.
- **The existing `capabilities` object** of `/auth/session` holds configuration flags (`main.py:539-549`). The shell
  hides Overview, Radar and Watchlist with it (`static/index.html:11385-11386`, `OWNER_PAGES`).
  - That object stays as it is, for the configuration.
  - The principal's access goes into a new `access` object:
    `{plan, role, status, expires_at, mfa_ok, capabilities:[…], limits:{…}, version, next}`.
  - Tabs are always shown (user decision); a tab without `<tab>.view` shows its example.
- **The `rights` wire field stays.**
  - `context.rights` is what the workers read today. They refuse unknown keys and values (`KNOWN_RIGHTS`,
    `apps/backtest-worker/src/server.ts:62`).
  - Phase 2 keeps the field and fills it with resolved capability names.
  - The workers' known names are extended **before** edge-bff sends new ones (deploy order: workers first).
  - The catalogs' `access:'admin'` marks (`screener/src/core/catalog.ts:78-79,141`, `backtest-worker/src/catalog.ts:72`)
    become `release` plus `capability` fields.
- **Browser storage added:** `edge.watchlist.view` (a user's list id), `edge.watchlist.logos` and `ml.symbol` in the new
  apps; all go into the storage registry. Overview, Radar and Watchlist `api.ts` also get the error contract (M471).
- **Build:** the radar, overview and watchlist Dockerfile stages copy only their own folder (`Dockerfile:42-69`). The
  shared session module needs COPY lines there and a path trigger in `.github/workflows/edge-bff-image.yml`.
- **CI gating:**
  - edge-bff and screener-worker deploy only on green checks (`checkSuites: true`).
  - backtest-worker, terminal-api and market-ai-orc are not gated. Their changes are tested locally and in CI before
    deploy by hand.
- **`EDGE_ADMIN_OWNERS`** is not declared in `.railway/railway.ts` (default: the one owner). The role-admin seed replaces
  it at cutover.
- **Static examples:** none exist yet for Overview, Radar, Watchlist, Screener, Backtest or Monitor. Phase 3 adds
  synthetic example files in the repository, served without a grant.

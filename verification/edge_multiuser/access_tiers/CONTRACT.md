## 0. Switch and invariants

- `EDGE_MULTIUSER` (edge-bff variable, default `false`).
  - **Off:** sign-in uses `EDGE_LOGIN`/`EDGE_PASSWORD_VERIFIER` exactly as today. The resulting principal is user #1
    (`owner_key = EDGE_OWNER`, role `admin`, every capability). Registration, code and reset routes answer 404.
  - **On:** sign-in reads `edge_bff.users`/`identities`.
- **`EDGE_SITE`** (edge-bff variable, `beta` default, or `live`; section 17). The decided pairing: the beta site runs
  with the switch off, the live site with it on; `config.validate` refuses any other pairing outside
  `EDGE_ENVIRONMENT=local` (where the tests run a switch-on beta). **Built** (`fix-site`).
- **Behaviour with the switch off is identical to today for the current user.** Test: the whole existing suite passes
  unchanged with the switch off (only the tests named in this contract may change).
- **The owner of a request comes only from the principal.**
  - No route, store call, worker call or Orc call reads `settings.owner` after Phase 1.
  - A test greps `apps/edge-bff/app` for `settings.owner`: the only allowed uses are the seed and the switch-off mapping in
    `app/principal.py`.
- **No plan or role name appears in code outside the catalog seed migration.** A test greps for the plan keys.
- Indicators keep being computed in the browser (user 2026-11-16). The server decides only which definitions, code
  chunks and data files a principal receives, and refuses ids outside the principal's capabilities.

## 2. Principal

```
Principal(user_id, owner_key, username, role, plan_key, status, expires_at, mfa_ok, capabilities: frozenset[str],
          limits: dict[str, value], version: str, token)
```

- **Resolution.** One query joins `sessions`, `users`, the active subscription, `plan_capabilities` and the overrides.
  - Switch off: `version` = `"env"`; capabilities = `{"*"}` (every capability). Only a session without an account
    (`user_id` NULL) of `EDGE_OWNER` resolves: a switch-on session of user #1 (pending MFA, idle, or of a disabled
    account) opens nothing on a switch-off site (built, `fix-site`, R2-1). A rollback to a build before Phase 1, which
    cannot have this check, first revokes every session `WHERE user_id IS NOT NULL` (section 17, rollback floors).
  - A `disabled` user, a revoked or expired session (absolute lifetime, both modes), or an idle session beyond
    `EDGE_SESSION_IDLE_SECONDS` (default 28800) answers 401.
  - An expired subscription, or one that has not started (`starts_at > now()`), resolves to the default plan (`free`).
  - On the live site every principal is masked to what the live site offers (section 17: no Monitor, no admin pages, no
    lab item, `*` included); built, `fix-site`.
  - A visitor without a session on the live site resolves to the guest principal: the `guest` plan's grants, for the
    Terminal routes it opens (section 9; built, track guest (`dec-guest`, integrated on `fix-int2`; not deployed)). Every other route keeps answering 401 without a session.
    - Only routes that ask for it admit a visitor: `auth.need(capability, guests=True)` and `auth.visitor`
      (`GET|POST /api/terminal/v1/{path}`, `GET /api/v1/catalog/{kind}`, `GET /api/v1/auth/guest`); the route walk
      (`tests/test_route_table.py` `GUEST_OPEN`) names them with their reason and fails on any other.
    - The guest plan is read on every guest request like every plan (`accounts.guest_plan`, `principal.guest_principal`),
      so a change of its rows applies on the next request; a visitor never holds `*`, `admin.access`, an admin right or
      a beta-only key (dropped and logged `guest_capability_dropped`), and never a lab item.
    - Who is a visitor: a request whose session cookie resolves to no session; a guest writes without CSRF (no session a
      cross-site page could ride; the Origin check of every write holds). Its owner key at terminal-api is `edge-guest`
      (`accounts.GUEST_OWNER`, never issued, refused for `EDGE_OWNER` and `EDGE_ADMIN_OWNERS`).
    - Its client address is the right-most `X-Forwarded-For` hop that parses as an address (`principal.client_of`);
      without one there is no guest (401). The socket peer counts only with `EDGE_ENVIRONMENT=local`. Open: the
      client-address probe of section 4 before guests are offered on live.
- **`last_seen_at`** is updated at most once per 60 s per session.
- **Dependencies** (in a new `app/principal.py`, used by every router):
  - `principal` replaces `session`;
  - `writer` replaces `write` (CSRF as today);
  - `need("<capability>", write=False)` refuses with `CAPABILITY_REQUIRED`;
  - `admin(write=…)` = `need("admin.access")` plus `mfa_ok`.
- **Router signature.** Routers move from `routes(app, session, write)` to `routes(app, auth)`. `auth` exposes
  `principal`, `writer`, `need` and `admin`. Inside a handler use `p.owner_key`, `p.can(cap)` and `p.limit(cap)`.
- **`request.state.owner`** (EXEC-BACKTEST-REVAMP P5) stays, set from the principal.
- **`rights.py`** (P5): `rights_of(settings, owner)` becomes `rights_of(principal)`, which reads capabilities. The right
  `flow_point_in_time` becomes the capability `backtest.flow_point_in_time`, granted to plan `admin` in the seed.
  `EDGE_ADMIN_OWNERS` stays as the switch-off source until the switch is on, then it is retired.

## 3. Error contract (every edge-bff refusal, including FastAPI's own)

- **Shape:** `{"error": {"code": "...", "message": "...", "details": {...}}}`. FastAPI's `HTTPException` and validation
  errors are mapped to this shape (M471).
- **Codes and how the front-end reacts:**

| Status | Code | Front-end reaction |
|---|---|---|
| 401 | `UNAUTHENTICATED` | go to sign-in |
| 403 | `CSRF_INVALID` | re-read the session once, retry once |
| 403 | `CAPABILITY_REQUIRED` (`details.capability`, `details.display_name`) | show the upgrade prompt; keep the session |
| 403 | `PLAN_EXPIRED` | show the upgrade prompt; keep the session |
| 403 | `MFA_REQUIRED` | ask for the code |
| 403 | `ORIGIN_REJECTED` | unchanged |
| 403 | `LIMIT_REACHED` (`details.limit`, `allowed`, `needed`) | a saved-item cap (waiting frees nothing): remove one or upgrade |
| 403 | `REGISTRATION_CLOSED` | the live site in pre-launch mode: registration opens soon (section 17; built, track guest (`dec-guest`, integrated on `fix-int2`; not deployed)) |
| 403 | `SIGN_IN_CLOSED` | the live site in pre-launch mode: only the admin and test accounts sign in (section 17; built, track guest (`dec-guest`, integrated on `fix-int2`; not deployed)) |
| 404 | `NOT_FOUND` | another user's item, so nothing reveals that it exists; on the live site also every beta-only route (section 17) |
| 429 | `LIMIT_REACHED` (`details.limit`, `retry_after_s`) | show the limit message and the wait |
| 429 | `SIGN_IN_RATE_LIMIT` (`details.retry_after_s`) | show the wait message (its words name the wait) |
| 503 | `TERMINAL_UNAVAILABLE` | terminal-api's own account or key failed (its 401, a 403 other than `capability_required`, its 5xx, a 2xx answer without the applied-header acknowledgement); never read as a sign-out |
| 503 | `SERVICE_UNAVAILABLE` (`Retry-After`) | too many requests in password work at once (sign-in, register, reset, change: at most 16; built, `fix-auth`, R2-37), or an unexpected server error (answered in this shape; the log gets method, path, class and SQLSTATE only, never the person's data; built, `fix-auth`, R2-25) |

- `Retry-After` is set on every 429 (and on the password pool's 503), with `details.retry_after_s` the same number. Test:
  `tests/test_contract_requirements.py` walks every answer built with 429 in `app/` (R2-40).
- **`LIMIT_REACHED`** is every plan limit's code: `details.limit` is the capability key (`terminal.layouts_max`,
  `backtest.queued_jobs`, `terminal.<quota>` ...), with `allowed` and `needed` where known; 429 with `Retry-After` when
  waiting frees it (the backtest queue, the Terminal quotas), 403 when it does not (a saved-item cap). The auth
  throttles' `LIMIT_REACHED` (`code_tries`, `mfa_tries`) name only the wait, never a plan (built, `fix-plans`, R2-39).
  A quota of 0 is 403 `CAPABILITY_REQUIRED` naming the limit, not 429 (built, `fix-terminal`, R1-22).
- **Relayed refusals:** edge-bff rebuilds every terminal-api answer it relays by one rule (`terminal_access.relayed`):
  a 429 becomes 429 `LIMIT_REACHED` with `details.limit` `terminal.<quota>`, `allowed`, `retry_after_s` and
  `Retry-After`; a 400 about the request 400 `INVALID_INPUT` and a 404 404 `NOT_FOUND`, each with terminal-api's code as
  `details.reason`; `capability_required` 403 `CAPABILITY_REQUIRED` with its display name; the rest 503
  `TERMINAL_UNAVAILABLE`. terminal-api's prose never reaches the page (built, `fix-terminal`, R1-1, R1-26).
- Messages are plain English, like every EDGE interface label (EXEC-UI-1019B, user: "Ok 1 aja"), in
  `static/edge-labels.js` (front-end) and `app/errors.py` (back-end); no internal names, no setting names. Corrected
  2026-11-16: the first draft said Indonesian. The rule holds for every message table of `app/` (errors, pages, the
  Terminal saves, the Screener, the Watchlist), tested by `tests/test_contract_requirements.py` (R2-40).
- **Words built from the code and its details** (`errors.words`, the one wording for people): `CAPABILITY_REQUIRED`
  names the item (`details.display_name`); `PLAN_EXPIRED` the item and the ended plan; `LIMIT_REACHED` the limit, the
  account's number and the wait; `MFA_REQUIRED` with `details.mfa_enrolled` false says to set the authenticator up. A
  worker's own sentence is kept unless it carries an internal key or family, then edge-bff words it (built,
  `fix-plans`, R2-15, R1-34). The display names come from the catalog, loaded at start and again when a route refuses.

**Registration rules:**
- Enumeration: an existing email or username gets the same 202. An existing email receives "Your EDGE account already
  exists" (the user's words were "akun sudah ada, gunakan Lupa Password"; English per EXEC-UI-1019B,
  `app/email_texts.py`).
- On the live site in pre-launch mode registration is closed, with a plain refusal on the page (decision 2026-11-19
  "Terbuka, tapi belum bisa mendaftar"; section 17; built, track guest (`dec-guest`, integrated on `fix-int2`; not deployed)): `register`, `register/verify` and a
  `code/resend` for `register` answer 403 `REGISTRATION_CLOSED`, the same for every address; the reset stays open (the
  test accounts set their passwords with it).
- Username taken: the conflict is decided at verify time. The pending registration with a taken username gets
  `USERNAME_TAKEN` only after the email code is proved (the code owner may choose another).
- Password:
  - 8 to 256 characters (user decision; NIST/OWASP ask 15 without MFA, which is recorded);
  - every character allowed, no composition rule;
  - refused when found in Pwned Passwords (k-anonymity range API `api.pwnedpasswords.com`, 2 s timeout). If the API
    fails, accept and log `PWNED_CHECK_UNAVAILABLE` (fail-open; recorded decision);
  - stored with scrypt N=2^14, r=8, p=5 (OWASP's minimum equivalent at 16 MiB; the main agent's design value, told to
    the user 2026-11-19; built, `fix-auth`, R2-29), the verifier naming its cost; an old verifier (p=1) is replaced at
    the next switch-on sign-in. Every check costs the same whatever the verifier's age.
- Phone: E.164, normalised; Indonesian `08…` becomes `+628…`; not verified.
- A `pending` user is deleted 24 h after creation if never verified.

**Codes:**
- 6 decimal digits from `secrets`, 300 s validity, at most 5 tries per code.
- A new code does **not** reset the failed count of the day (NIST): at most 20 failed tries per user per day, then codes
  are refused for 24 h (`LIMIT_REACHED`).
- Resend at most once per 60 s and 10 per day per email; the 60 s gap is between code emails only (built, `fix-auth`,
  R2-10). One pending registration is mailed at most 3 times a day (its code, resends, restarts; R1-13).
- The 20-a-day cap of failed tries also holds per address for resets, account or not (R1-8); `USERNAME_TAKEN` uses one
  of the code's 5 tries (R1-12).
- Codes are compared in constant time.

**Throttle** (Postgres, works with several replicas):
- Sign-in: 10 failures per login and client address per 15 min (enforced; built, `fix-auth`, R1-9: a login alone let
  anyone keep the owner out), and 30 per IP hash per 15 min (recorded only, below). A reset proved by its email code
  clears the resetting client's counts of the account's login names.
- Per account (switch on): at most 100 consecutive failed passwords, then a 24 h lock answered as a wrong password;
  after it the count restarts at 90; cleared by a success, a reset by email code or a change (built, `fix-auth`,
  R1-16). The beta (switch off) has no such cap, which keeps the admin's long random password (the main agent's design
  value, told to the user 2026-11-19).
- Email sending: 10 per IP hash per hour.
- A dummy scrypt verify runs for unknown logins, so timing matches.
- **Client IP:** from `X-Forwarded-For` as set by Railway's edge (right-most untrusted hop), read over every line of the
  header (a line the client writes before the edge's never decides) and keyed by the whole IPv4 address or the IPv6 /64
  (`throttle.forwarded_hop`, `address_key`; the visitor key and the sign-in and reset counters read it the same way; 3c
  check C3-5). Until a probe proves what Railway sends (Phase 0 task, M470 notes; the user's "1a" 2026-11-20: run it
  before the live site opens to visitors, with a client-written header sent once as one line and once as two), the
  per-IP sign-in limit is recorded in the table but not enforced; the per-account limits are enforced. The probe result
  is recorded in `ERRORS_AND_SOLUTIONS.md`.

**Sessions:**
- Absolute lifetime 24 h (today), in both modes; idle timeout 8 h; at most 5 sessions per user (the oldest is revoked).
  Tests: `tests/test_contract_requirements.py` (an expired session answers 401 in both modes, R2-40).
- Revoke all on password change or reset, disable, or role change.
- A reset, a change, a sign-out everywhere, a sign-in and an MFA verify take the account's `users` row as their lock and
  check their proof inside the same transaction; one whose proof no longer holds is refused (built, `fix-auth`, R2-9).
- The SSE stream re-checks the principal on each loop (it already re-reads the session, `main.py`), with the
  capability the route needs (`monitor.view`): held by `tests/test_run_stream_live.py` (built, `fix-records`, R1-28).
- **Cookies:** on an https origin `__Host-edge_session` and `__Host-edge_registration` (Path=/, no Domain, Secure);
  local http keeps the plain names. With the switch off a session under the old name is moved once (the admin is not
  signed out); with it on the old name is never read (built, `fix-plans`, R2-22).
- An https origin sends `Strict-Transport-Security: max-age=31536000` (host only, no preload; built, `fix-plans`,
  R2-21). Every page policy has `form-action 'self'`; the shell runs no inline script (`script-src 'self'`; R2-19).

**Admin MFA:**
- TOTP (RFC 6238, SHA-1, 30 s, 6 digits, ±1 step, `last_step` replay guard).
- Required for role `admin` before any admin route. The current user (#1) enrols on first sign-in with the switch on.
  Switch off: no MFA, as today. The admin may sign in on the live site, with MFA (the main agent's design value, told to
  the user 2026-11-19; the live mask still hides the Monitor and the admin pages there, section 17).
- A session waiting for its second factor may use only the session read, sign-out, enrol and verify (`MFA_OPEN`).
- The cap of failed codes is decided and counted under one lock of the enrolment (built, `fix-auth`, R2-12); a code
  confirms only the enrolment whose secret it was checked against (R2-11).
- A new authenticator beside a confirmed one needs the second factor passed within the last 10 minutes
  (`auth_flows.MFA_RECENT_SECONDS`; the main agent's design value, told to the user 2026-11-19, EXEC.md "Decisions after
  the fix round"): the request's session `mfa_passed_at` is read under the enrolment's row lock, by the database's
  clock. An older pass, or none, is 403 `MFA_REQUIRED` with `details.mfa_enrolled` true and `details.recent_s` 600, and

  session passed now, and the `/mfa` page then starts the set-up again by itself. The first enrolment (no confirmed
  authenticator) needs no recent pass (built, track decisions; `tests/test_decisions_small.py`, and the re-check's own

## 2. M82: horizon dikunci dari bacaan router (permanen)

- **Akar masalah:** gerbang rencana membaca horizon dengan pola kata. Router sudah membaca pesan, tetapi hanya
  mengeluarkan teks bebas (`revision_instruction`).
- **Perbaikan:**
  - Router percakapan mengeluarkan `design_value_changes`: `[{name: OUTCOME_HORIZON, value, unit, action: REPLACE|ADD}]`,
    dengan skema ketat. Nilai tidak valid diabaikan dan tidak menggagalkan routing.
  - Gerbang memakai bacaan router:
    - REPLACE: nilai router menggantikan horizon sebelumnya;
    - ADD: horizon sebelumnya ditambah nilai router.
  - Pola kata tetap dipakai sebagai pemeriksa silang. Bila keduanya tidak sepakat, **keduanya diizinkan** dan dicatat
    di log `plan_horizon_readings_disagree`, karena mengunci nilai yang salah lebih buruk.
  - Tanpa bacaan router (pesan pertama, aksi API eksplisit, router gagal): perilaku sekarang dipakai, yaitu
    pernyataan terbaru menang.
- **Risiko yang ditutup:**
  - horizon tambahan tidak lagi menghapus horizon lama;
  - jendela syarat atau lookback ("setelah 3 hari turun", "jangka waktu 3 bulan") tidak lagi melepas atau mengganti
    horizon.
- **Risiko baru:**
  - token keluaran router naik sedikit;
  - router salah baca (mitigasi: pemeriksa silang dan log).
- **Wajib sebelum deploy:**
  - benchmark router (`scripts/benchmark_turn_router.py`) dengan kasus horizon ganti, tambah dan lookback;
  - `AI_ROUTER.md` di-generate ulang;
  - tes penuh orc.
- **Verifikasi live:** percakapan s3 ("ubah horizonnya jadi 10 hari"), satu kasus "tambah 20 hari", dan satu kasus
  lookback.

## 4. Database dulu, baru web

**Tujuan:** bila data ada di tabel (contoh nanti: daftar saham grup Bakrie), AI tidak mengambilnya dari web.

### Benchmark eksternal

| Sumber | Pola |
|---|---|
| [Adaptive RAG + Corrective RAG (LangGraph, Mistral cookbook)](https://docs.mistral.ai/resources/cookbooks/third_party-langchain-adaptive_rag_mistral) | Router memutuskan sumber per pertanyaan. Bila sumber internal relevan, web tidak dipakai; web hanya jatuhan setelah hasil internal dinilai tidak cukup |
| [Contoh Adaptive+Corrective RAG](https://github.com/yevsel/agentic-RAG-v1) | Bacaan internal dinilai relevan atau tidak sebelum jatuh ke web |
| [OpenAI file search + web search](https://team400.ai/blog/2026-04-openai-file-search-vector-stores-responses-api) | Pengetahuan internal dicek dulu; web untuk yang tidak terjawab |
| [Microsoft 365 Copilot](https://learn.microsoft.com/en-us/copilot/microsoft-365/microsoft-365-copilot-transparency-note) | Jawaban berbasis data kerja; web grounding dipakai selektif untuk yang di luar batas data internal |

**Pola bersamanya:** urutan sumber diputuskan sistem, bukan diserahkan ke model, dengan sumber internal lebih dulu.
Web hanya menjadi jatuhan setelah ada pemeriksaan bahwa sumber internal tidak menjawab.

### Kondisi sekarang

- Hanya deskripsi alat yang melarang ("never use it for prices, volumes or any figure the database holds").
- `find_web_fact` tidak mengecek katalog sama sekali.

### Usulan (permanen, belum dikerjakan)

Pemeriksaan katalog **di dalam alat web**, di lapisan backend:
- Sebelum mencari di web, backend mencocokkan atribut yang diminta dengan katalog. Sumbernya Column_Catalog (kolom
  DIMENSION, deskripsi) dan nilai dimensi, **diturunkan dari katalog, bukan daftar**.
- Bila katalog punya kolom yang menjawab, alat mengembalikan REJECTED dengan `next_action CALL:get_dimension_values`
  yang menyebut tabel dan kolomnya.
- Pencocokan memakai satu panggilan kecil (DeepSeek low, skema ketat, ± USD 0,0005) atas daftar kolom dimensi katalog.
- Kolom grup baru (misalnya Bakrie) yang terdaftar di katalog otomatis tercakup **tanpa perubahan kode**.

Ditambah aturan "web hanya deskriptif":
- angka dari fakta web tidak boleh masuk kode perhitungan; gerbang menolaknya;
- daftar entitas dari web yang dipakai menyaring perhitungan diberi tanda "Fakta web".
